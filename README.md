# 과제 13: 병합 정렬과 퀵 정렬의 성능 비교

## 실행 방법
```
gcc -O2 -fno-optimize-sibling-calls -o sort_compare sort_compare.c
./sort_compare
```
`-fno-optimize-sibling-calls`는 컴파일러가 퀵 정렬의 두 번째 재귀 호출을 반복문으로 바꿔 재귀 스택 사용량이 줄어드는 것을 막기 위한 옵션입니다.

## 구현 및 측정 방법
- 데이터: 0 ~ 999,999 범위의 무작위 정수(중복 허용), n = 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000
- 각 n에서 네 알고리즘(병합, 퀵 First/Random/Median-of-Three)은 같은 원본의 복사본을 사용하고, 정렬 후 오름차순을 검증
- 퀵 정렬은 과제 12와 같은 구현(피벗 선택만 다르고 Lomuto 분할은 동일)
- **비교 횟수**: 병합 정렬은 병합 중 `a[i] <= a[j]` 비교, 퀵 정렬은 분할 중 `a[j] < pivot` 비교와 Median-of-Three의 중앙값 결정 비교를 셉니다. 반복문 조건과 난수 생성, 데이터 이동은 제외합니다.
- **실행시간**: `clock_gettime(CLOCK_MONOTONIC)`로 정렬 함수 호출 전후만 측정하고, 배열 복사와 출력 시간은 제외합니다. 시간이 매우 짧아서 같은 데이터를 200번 정렬한 평균(ms)을 사용합니다.
- **메모리 사용량(추가 메모리)**: 원본 배열은 제외하고 다음 두 가지를 더합니다.
  1. 임시 배열: 병합 정렬은 `n × sizeof(int) = 4n` Byte를 직접 계산합니다. 퀵 정렬은 임시 배열이 없어 0입니다.
  2. 재귀 호출 스택: 재귀 함수가 호출될 때마다 지역 변수의 주소를 읽어 가장 깊이 내려갔을 때의 주소를 기록하고, 시작 주소와의 차이를 최대 스택 사용량(Byte)으로 사용합니다. (별도의 한 번의 실행에서만 측정하여 시간 측정에 영향을 주지 않습니다.)
  - 한계: 재귀 함수 안에서만 측정하므로 맨 아래에서 호출되는 `partition`/`merge`의 프레임은 포함되지 않아 실제보다 조금 작게 나오며, 프레임 크기는 컴파일러와 최적화 옵션에 따라 달라집니다.

## 분석

### 1. 비교 횟수
n이 2배가 될 때 네 알고리즘 모두 비교 횟수가 2배보다 약간 더 늘어나, O(n log n)과 일치합니다. 병합 정렬은 모든 n에서 퀵 정렬보다 비교 횟수가 적었습니다(n=20,000에서 First 대비 약 20%, Median3 대비 약 16% 적음). 병합 정렬은 항상 구간을 정확히 절반으로 나누어 트리 깊이가 log₂n으로 고정되고, 병합 한 번에 최대 (길이−1)번만 비교하기 때문에 비교 횟수가 n log₂n − n 근처(n=20,000: 약 265,754, 측정 260,970)입니다. 퀵 정렬은 피벗이 구간을 치우치게 나누는 경우가 있어 평균적으로 약 1.39 n log₂n(2n ln n)까지 늘어나며, 한 번 분할할 때마다 구간 전체를 피벗과 비교하기 때문에 비교가 더 많습니다.

### 2. 실행시간
비교 횟수는 병합 정렬이 적었지만, 실행시간은 First와 Median3 퀵 정렬이 대체로 더 빨랐습니다(n=20,000에서 First 1.27 ms, 병합 1.80 ms로 병합이 약 1.4배). 숫자 비교 횟수가 시간을 결정하지 않기 때문입니다. 병합 정렬은 비교는 적어도 결과를 임시 배열에 쓰고 다시 원본으로 복사하는 데이터 이동이 매번 발생하고 별도 배열을 오가며 캐시 효율이 떨어집니다. 반면 퀵 정렬은 제자리에서 교환하며 배열을 순차적으로 훑어 캐시 지역성이 좋고, 비교 횟수 차이보다 이동·복사 비용 차이가 더 크게 작용했습니다. Random 피벗은 분할마다 `rand()`를 호출하는 비용(비교 횟수에는 포함되지 않음) 때문에 병합 정렬과 비슷하거나 느렸습니다.

### 3. 메모리 사용량
병합 정렬은 임시 배열 4n Byte가 필요해 n에 비례해 늘어났고(1,000 → 5,000 Byte, 20,000 → 81,400 Byte), 재귀 스택은 깊이 log₂n에 호출당 약 90 Byte 정도(n=20,000에서 약 1,400 Byte)로 작았습니다. 퀵 정렬은 임시 배열이 없고 재귀 스택만 써서 1.5~3 KB 수준이며 n이 20배가 되어도 2배 안쪽으로만 늘었습니다. n=20,000에서 병합 정렬은 퀵 정렬의 약 30~40배 메모리를 사용했습니다. Median3의 스택이 First나 Random보다 작은 것은 분할이 더 균형 잡혀 재귀 깊이가 얕았기 때문입니다.

### 4. 퀵 정렬의 피벗 선택 방법에 따른 차이
Median3는 n=1,000을 제외한 모든 n에서 비교 횟수가 가장 적었습니다. 세 값의 중앙값은 극단값일 가능성이 낮아 분할이 더 균형 잡히기 때문입니다. n=1,000에서는 중앙값을 정하는 데 드는 추가 비교(분할당 2~3회)의 비중이 커서 가장 많았습니다. Random은 First보다 대체로 적었으나(20,000 제외) 차이는 작았고 무작위 데이터에서는 두 방법의 분할 균형이 통계적으로 같습니다. 이미 정렬된 입력에서는 First가 O(n²)으로 나빠지지만 Random과 Median3는 영향을 덜 받습니다. 실행시간은 Median3가 First와 비슷했고, Random은 `rand()` 비용 때문에 느렸습니다.

### 5. 시간 복잡도와 공간 복잡도

| 알고리즘 | 시간(평균) | 시간(최악) | 공간 |
|---|---|---|---|
| 병합 정렬 | O(n log n) | O(n log n) | O(n) (임시 배열) |
| 퀵 정렬 | O(n log n) | O(n²) | O(log n) 평균, 최악 O(n) (재귀 스택) |

병합 정렬은 입력에 관계없이 항상 같은 성능을 보장하지만 추가 메모리가 필요하고, 퀵 정렬은 추가 메모리가 거의 없고 평균적으로 빠르지만 피벗 선택이 나쁘면 최악의 경우가 생길 수 있습니다. 실험 결과도 이 차이와 일치하여, 퀵 정렬은 비교 횟수는 더 많아도 메모리와 실행시간에서 유리했고, 병합 정렬은 비교 횟수가 가장 적고 성능이 안정적인 대신 메모리를 많이 썼습니다.
